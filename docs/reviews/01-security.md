# Security specialist review

Scope: blueprint docs only (decisions, advisors, access matrix, build order, 12 module READMEs, P0 task specs). No code exists, so every finding is a design or planning risk. Existing control intent is strong; the problems are decision drift, unspecified key and credential mechanics, and P0 modules that carry the most security weight (identity, access, audit, uploads) having no tasks.

## Verdict

The security design intent is sound (FORCE RLS, non-owner role, SET LOCAL, quarantine pipeline, hash-chained audit, AI register), and the tenancy and database P0 tasks are well specified. The blueprint is not yet safe to build from. Several owner decisions are stale carry-overs from the Python plan (Alembic, arq/Celery, pyHanko, SECURITY-08 in pytest/pip-audit) and one is a real security regression (shared key with tenant prefixes, which breaks crypto-shred, per-tenant export encryption and the IRAP/Rio Tinto story). Identity is internally contradictory (decision says Keycloak; the access matrix, identity README and portal README still say WorkOS). The P0 modules that hold the highest-risk controls (identity, access, audit, uploads, approvals, projects) have no tasks, while P0 exit criteria depend on them. Fix the key-scheme and identity ADRs and add the missing tasks before Phase 0 starts.

- tasks/DATABASE-02 policy `current_setting('app.tenant_id', true)::uuid`: an empty string raises a cast error (fail-closed but noisy and can mask bugs, and some code paths may catch it). Use NULLIF. ## Recommended decisions / ADRs

1. **ADR: Tenant key scheme = per-tenant KMS envelope keys.** Recommendation: reverse "shared key with tenant prefixes" for data at rest; use one KMS CMK per tenant (cheap at 500-5000 users scale of tenants, tens of tenants) or a per-tenant data key wrapped by a regional CMK, with encryption context `tenant_id`. Rationale: enables real crypto-shred, per-tenant export encryption, IRAP evidence, and a bucket/key policy boundary independent of app bugs. Keep prefixes for naming. Legal hold blocks key schedule-deletion.
2. **ADR: Identity = Keycloak, with SCIM and tenancy design.** Recommendation: Keycloak on Fargate (HA, own RDS, no public admin), realm layout decided, SCIM implemented as a thin NestJS service driving Keycloak admin API (or vetted extension), IdP-initiated deprovision calls session/token/link revocation in one transaction with a tested SLA (<=5 min, target <=60 s). Remove all WorkOS references. Rationale: avoids two sources of truth and meets residency.
3. **ADR: Credential policy for bearer accounts.** Fix entropy, TTL, device binding, lockout, rate limits, idle/absolute timeouts per account class, which actions require step-up and which are barred for PIN/magic-link users (hold-point signing, exports, approvals). Rationale: matrix and identity docs currently contradict.
4. **ADR: Data-store role model.** Roles: migrator (DDL only, not used by runtime), app (RLS enforced), worker (RLS enforced, tenant context per job), dispatcher (narrow, audited, can only enumerate tenants), readonly/analytics (RLS enforced, no BYPASSRLS), audit_writer (INSERT only into audit). Rationale: closes risk #1 and defines the one allowed cross-tenant path.
5. **ADR: Tamper-evidence architecture.** Chain in audit module per tenant; signing attestations reference chain; anchor in a separate AWS account with Object Lock (governance during pilot, compliance after retention schedule signed off); RFC 3161 TSA; offline verifier; PAdES keys in KMS with sign-only role and CloudTrail alerting. Define legal hold > purge > crypto-shred precedence.
6. **ADR: AI gateway and provider.** Bedrock Sydney only for AU tenants, direct vendor API forbidden for tenant data; AI off by default; redaction and classification enforcement in gateway; agents read-only; logs of prompts classified and retention-bound.
7. **ADR: Reconcile Python-era decisions.** Replace Alembic with a TS-native SQL migration runner (e.g. node-pg-migrate, Drizzle kit with raw SQL, or Atlas) and BullMQ; strike pyHanko or ratify a signing sidecar and its network posture.
8. **ADR: When a tenant must be siloed.** Written trigger (IRAP PROTECTED, Rio Tinto direct contract, contractual requirement) and the commitment that schema stays shape-neutral; a siloed shape is a deploy variant, not P0 work.
9. **ADR: Outbound and egress.** Single egress proxy with allowlist for webhooks, connectors, AI and converter workers; converters have no route out.
10. **ADR: Super Admin / support access.** Separate operator tenant and console; JIT, ticketed, tenant-approved, time-boxed access; audit stream visible to tenant.

2. Keycloak is decided, but docs assume WorkOS and SCIM. Do you accept building/maintaining SCIM against Keycloak, or do you want WorkOS back for SSO and SCIM, with Keycloak only for local/field accounts?
3. Does Rio Tinto (or any early customer) contractually require siloed infrastructure, Australian-only support staff, or a named pen test before go-live? Who is the decision-maker on siloed triggers?
4. Retention periods per record type (needed before Object Lock compliance mode) and which time authority for signatures. Does Kaefer's contract name a signature standard?
5. Can field PIN/magic-link users ever sign hold points or only capture data? This sets step-up and credential policy.
6. Is "direct model vendor API" an intentional choice (if so, which vendor and region, and will AU tenant data go to it?) or should it be Bedrock Sydney?
7. Telegram connector: drop? Restore/import-from-export: build or not (hostile data and cross-tenant restore risk)? Dual approval for every full export?
8. Who is the named security owner (vCISO or internal) for SOC 2 Type I, and is the target date tied to the Kaefer pilot start?
9. Will real Kaefer data ever touch Coolify or a developer laptop (migration from AIP)? If so, define the migration environment now.
10. Should the matrix's Client Reviewer `approve` rights beyond hold-point witness/counter-sign be trimmed for first release to match the decided portal scope?
