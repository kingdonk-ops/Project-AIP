# Data-tier stack specialist review

Scope: PostgreSQL, ORM/migrations, Redis/jobs, search, pooling. Blueprint only, no code exists.

## Verdict

The data design (pooled RLS, forced policies, non-owner app role, outbox, append-only audit, snapshot tables) is sound and TypeScript-neutral. The stack wording is not. It is half Python: Alembic, arq/Celery, SQLAlchemy mixins, `.py` paths and pytest-style tests survive in about 20 tasks and in the database, ops and arch modules, even though the owner chose a TypeScript rebuild. `07-task-conventions.md` says "ADR 0002 wins", but `docs/adr/` does not exist, so the override has no authority behind it yet.

Recommendation, in one line: **Kysely over node-postgres for queries; forward-only plain-SQL migrations run by dbmate or node-pg-migrate; BullMQ as job transport with job state in Postgres; a Postgres outbox dispatcher feeding BullMQ; PgBouncer in transaction mode (or direct bounded pool) rather than RDS Proxy on the RLS path, with only `set_config(..., true)` inside explicit transactions.** Details below. Fix the contradictions before any task starts, because DATABASE-02, TESTING-01 and ARCH-05 are the first things built and every later migration inherits their shape.

## RLS / pooling implementation notes

- **Always inside an explicit transaction.** `set_config('app.tenant_id', $1, true)` outside `BEGIN` is a no-op after the implicit statement ends. Never use plain `SET`/`set_config(..., false)` on a pooled connection: it leaks to the next tenant in transaction pooling mode. CI lint: grep for `set_config(.*false)` and `SET app.` (non-LOCAL).
- **PgBouncer transaction mode** is compatible with `SET LOCAL`. Pitfalls: no session advisory locks (use `pg_advisory_xact_lock`), no `LISTEN/NOTIFY` through the pooler (use a direct connection for the dispatcher), no session-level prepared statements (pg driver named statements break; use `max_prepared_statements` in PgBouncer 1.21+ or disable named statements), no `SET ROLE` without LOCAL, no temp tables across transactions, `search_path` must be set per role (`ALTER ROLE app SET search_path`) not per session.
- **RDS Proxy**: pins the session when it sees session-level `SET`, advisory locks, temp tables, or (for some drivers) multi-statement/extended-protocol edge cases. `SET LOCAL`/`set_config(...,true)` in an explicit transaction does not pin in current behaviour, but verify by the `DatabaseConnectionsCurrentlySessionPinned` metric under load in staging. Also note: RDS Proxy has no pooling benefit with Fargate at this scale (max a few hundred conns); ask whether it is needed at all. IAM auth via Proxy is its main value, which can instead be done with RDS IAM tokens or Secrets Manager.
- **Fail closed**: policy `USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)`. Unset gives NULL, so zero rows (not an error and not all rows). Also add `WITH CHECK` with the same expression on every policy (the template must say this; INSERT/UPDATE otherwise relies on USING only). Wrap in a `STABLE` SQL function `app_tenant_id()` so the planner caches it, and index `(tenant_id, ...)` leading on every table.
- **Roles**: `migrator` owns objects; `app` is NOLOGIN-group inherited by a login role, no BYPASSRLS, not owner, and `ALTER TABLE ... FORCE ROW LEVEL SECURITY`. Also `REVOKE CREATE ON SCHEMA public FROM PUBLIC`. Superuser-like `rds_superuser` is never used by the app. Separate roles for dispatcher (cross-tenant outbox poll) need a deliberate policy: either `BYPASSRLS` on a narrow role limited by column grants, or SECURITY DEFINER functions. Choose one and document it; DATABASE-02 creates "dispatcher" without saying which.
- **Cross-tenant workers**: BullMQ payload carries `tenantId`; the worker opens `withTenant()` per job. Never reuse an open transaction across jobs. Jobs that scan all tenants (retention purge, snapshot refresh) iterate tenants and run one transaction each.
- **ORM transaction discipline**: a `Trx`-typed parameter on every repository method makes it a compile error to query without a tenant transaction. Do not expose the root Kysely instance outside `platform/db`. Add a lint rule banning `pool.query` outside it.
- **Testcontainers**: run the suite against PgBouncer in transaction mode too (DATABASE-02 already asks for this; keep it as a CI job, not a one-off). Add a test that a statement outside `withTenant` returns zero rows, and a leak test with 1 server connection and alternating tenants.
- **ltree**: `ltree` and `vector` have no TS type support; write small codecs. Subtree move as one `UPDATE ... SET path = new || subpath(path, nlevel(old))` guarded by an advisory xact lock on the tenant and a `path <@ old` predicate. Index `GIST (path)` plus `(tenant_id)`; remember GiST on ltree does not combine with tenant_id equality unless `btree_gist` is installed.
- **pgvector**: HNSW index per table, tenant filter is applied after index scan and can under-return; use `hnsw.iterative_scan` (pgvector 0.8, available on RDS PG16/17) or partial/partitioned indexes for large tenants. Test recall with a small tenant next to a big one.

## Schema & conventions feedback

- Primary keys: use UUIDv7 (generated in app or via `uuidv7()` on PG18) for insert locality and time-partition friendliness; avoid v4 on high-volume tables (responses, audit, activity, sync_operations).
- Partitioned tables: PKs and unique constraints must include the partition key; RLS plus FORCE must be set on each partition or the parent only (policies on the parent apply when querying the parent but not when partitions are accessed directly: revoke direct grants on partitions). DATABASE-05 should cover this and add automation (pg_partman or a scheduled job) for creating future partitions.
- Hash-chained audit: the chain needs a serialised writer per tenant (or per chain id) and a deterministic canonical serialisation (RFC 8785 JSON canonicalisation). Concurrent inserts break `prior_hash`. Use one `audit_chain_heads` row per tenant locked `FOR UPDATE` in the audit-writer transaction, or a single-consumer dispatcher per tenant. Partitioning plus per-tenant chain is fine. Record the hashing function version in each row.
- Append-only enforcement: `REVOKE UPDATE, DELETE, TRUNCATE` plus a `BEFORE UPDATE OR DELETE` trigger raising an exception (defence if a grant slips). `domain_events` is not purely append-only (published_at, attempts change); the plan of column-level grants for the dispatcher is correct, so make sure payload is excluded.
- Soft delete: every unique index must be partial `WHERE deleted_at IS NULL`; add to the template and the checker. The "every table has soft delete" convention conflicts with partitioned/history tables; list exemptions in `schema_convention_exceptions` up front.
- `schema_convention_exceptions` and `rls_coverage_reports` are platform tables without tenant_id; they need grants rather than RLS, and are the right place to document an exemption path. Their IDs are uuid, fine.
- `sync_version int`: use `integer` with a trigger or explicit increment in the UPDATE (`WHERE sync_version = $expected`), and `bigint` if offline replay may exceed 2^31 (unlikely, keep int). `updated_at` should be set by trigger, not application, to survive raw SQL.
- Snapshot reporting tables: refresh per tenant in batches inside `withTenant`; avoid `REFRESH MATERIALIZED VIEW` (no RLS on matviews, cross-tenant by nature). Confirm the decision uses plain tables, and give them the same template. State the staleness SLA.
- History tables storing `snapshot jsonb` of full rows will bloat; consider storing diffs or partitioning by `valid_from`; GiST on `tstzrange` needs `btree_gist` to include `tenant_id`.
- Encryption: "shared key with tenant prefixes" plus "crypto-shred" in legal-hold copy are incompatible (cannot shred one tenant with a shared key). Flag to the security reviewer.
- Pin PostgreSQL major (16 or 17) and the RDS extension list now; confirm `pgvector` and `ltree` versions on RDS for the chosen version. Single-AZ staging, Multi-AZ prod, PITR on, and a parameter group with `rds.force_ssl=1`, `log_statement=ddl`, `pgaudit` for SOC 2.
